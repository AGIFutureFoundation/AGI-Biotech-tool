What happens when a source does not answer

The Data Sources page claims a failed lookup is reported as failed and never filled with a plausible number — the second published claim in two iterations with nothing behind it. It is checkable offline, because what is under test is how the module behaves when a request fails, and a stubbed fetch fails on demand more reliably than a real one.

  • A POST is never replayed through the read-only proxy. Re-sending a request body because the first attempt looked like a CORS failure is a silent duplicate submission — pinned down by two cases, for a thrown failure and an HTTP status
  • 404 and 503 throw, naming the host that failed and the status, so a failure cannot read as "this protein has no data"
  • "No hits" stays distinguishable from "could not ask" — both representable, and not alike
  • One proxy retry for the URL originally wanted, not a loop; no retry after an abort, so a timeout is not served twice
  • Failures evicted from the cache, so one flaky moment does not poison a source for the session
  • PDB-to-mmCIF fallback that still fails when neither exists, rather than handing back empty text that would parse to a zero-atom structure
  • Found while testing: the fallback catches any GET failure, not only a CORS refusal, so a 502 is retried through the proxy too — one lookup can cost two requests. Now a test and a wiki note
  • Mutation-checked: removing the body guard fails both POST cases. 179 JavaScript tests and 1438 Python tests passing
  • The providers against live services. These prove the module handles failure honestly; they say nothing about whether an endpoint still returns the shape expected. Response-shape drift at a public API is the likeliest way this layer breaks and cannot be caught from here

Tamper detection that is actually tested

The ledger is the project's central honesty mechanism. Every traceability claim rests on one property — alter a record and verification fails — which the wiki asserted, the whitepaper asserted, and nothing checked. A tamper-evident log whose tamper detection is untested is decoration. So the tests tamper: edit a score, delete the caveat, reorder, splice, renumber, forge the header.

  • Each caught at the right index with the right reason. Deleting the "not kcal/mol" caveat is caught like any other edit — it is a hashed field, not a note on a page
  • The careful forger's move — edit a payload and re-hash to cover it — still fails at the following record, whose link now dangles
  • New js/ledger-verify.js: the export format promised a root hash you could "later verify" and there was nothing to verify it with. It now checks a document on its own, plus the claimed head and length against the records actually carried
  • The honest limit, now documented: removing records from the end leaves a chain that verifies perfectly. That is a property of hash chains, it was nowhere in the docs, and it is now the only "no" in the wiki's detection table
  • An external head hash closes it; without one, every result says in as many words that end-removal would not show
  • Proven not assumed: an export survives a JSON round trip and still verifies, and the standalone verifier agrees with the live one — the guard against the two canonical forms drifting apart
  • Mutation-checked: removing the re-hash comparison fails two cases. 161 JavaScript tests and 1438 Python tests passing
  • Anchoring a head hash anywhere external, which is the only thing that makes truncation detectable in practice. Needs a network and a counterparty
  • The ledger proves provenance, not correctness. A tamper-evident record of an unvalidated docking score is an unvalidated docking score

The stage upstream of everything

The structure parsers were the last untested stage, and the only one upstream of pocket detection. A column misread there does not announce itself — it arrives at the other end as a slightly wrong answer that looks like a slightly wrong score. Fixtures were hand-written from the PDB format specification rather than from the implementation, so the expectations come from the format.

  • Found and fixed: PDB insertion codes were dropped. ALA 100 and ALA 100A collapsed into one residue, which silently kept only the second C-alpha it saw
  • Antibody CDR loops are numbered 100, 100A, 100B — so half an inserted loop rode on the wrong elastic-network anchor, residue counts came out short, pocket labels named one residue for two
  • Now read from column 27 in PDB and pdbx_PDB_ins_code in mmCIF, so both formats group residues identically, with a ready label of the form ALA100A
  • Coordinates packed with no separating space, -123.456-123.456, still parse as three numbers — proof the parser is column-based, not splitting on whitespace
  • An atom named CA is carbon in a residue and calcium as an ion, decided by which column the letters start in, which is the real PDB convention
  • altLoc, multi-model, HETATM standard residues promoted to polymer, waters and ions, CONECT honoured where distance perception would not bond, junk input parsed to an empty structure
  • Mutation-checked: reverting the residue key fails both insertion-code tests
  • The JS-to-Python scoring cross-check on real crystallographic geometry still passes, so the regrouping shifted no score. 140 JavaScript tests and 1438 Python tests passing
  • The parsers against real RCSB files, where the awkward cases live — multi-character chain IDs, hybrid-36 serials past 99999, structures with over 62 chains. Those need the network

Landing the fix, and measuring that it barely matters

The exact planarity term is now in js/md.js, the superseded implementation removed rather than left unused, and the test that recorded the defect replaced by the test that proves the fix. Then the question iteration 12 left open — does it change any result a user sees? — was measured rather than assumed, and the answer is almost none.

  • ligandForces as a whole is gradient-exact to under 1e-6 at every pyramidalisation tested; the same check failed at 6.26e-2 before the swap
  • Momentum still conserved to 1e-9; the old in-place implementation asserted gone, not just unused
  • Mutation-checked: reinstating the old term inline fails the new test, and md.js was restored to exactly the intended 5-insertion, 13-deletion swap
  • Measured impact: minimising a two-sp2-centre fragment from three distortions, residual out-of-plane is at most 0.001 Å either way, energies agree to 0.001, geometries differ by 0.002–0.006 Å RMSD. Both terms flatten the centre; they disagree only about the force on the way, and FIRE's line search absorbed it
  • 123 JavaScript tests, 1438 Python tests, and the JS-to-Python scoring cross-check all passing
  • So: the fix is correct and removes a latent hazard, and it is not a result anyone would notice. Both halves belong in the record
  • Energy conservation over a long trajectory is where an inexact force would show most. The thermostat dominates at these timescales, so measuring it means the OpenMM comparison — which needs the server

iter 12

The force must be the gradient, and in one place it was not

A force field has one property worth more than the others: the force must be the negative gradient of its energy. When it fails, nothing in the output says so — the molecule just behaves slightly oddly in a way that reads as physics being hard. A central finite difference in double precision at three step sizes makes the convergence visible rather than assumed: 3.18e-5 at h=1e-3, 3.18e-7 at 1e-4, 2.27e-9 at 1e-5. Bonds, angles and repulsion are exact. The planarity term was not.

  • Found: js/md.js holds its plane normal fixed, so the force misses the normal's own motion — 19% off its energy gradient at 0.3 Å of pyramidalisation, worst where a minimiser lives
  • Nearly missed: the first check read 3e-10 because that geometry's errors cancelled. Pyramidalising the centre alone exposed it
  • js/planarity.js is the corrected term, gradient-exact to 1e-7 and momentum-conserving to 1e-12, held as a new file because another session is working in md.js
  • The defect is asserted as a bounded fact, so the number cannot drift unnoticed
  • Newton's third law to 1e-9; exact spring and repulsion energies; the law-of-cosines 1-3 distance
  • 400 steps with no NaN and both bonds intact; a frozen protein that moves by not one float
  • The steric guard bounds its shift to 0.25 Å and skips coincident atoms instead of dividing by zero
  • 121 JavaScript tests and 1438 Python tests passing
  • Whether the fix changes any result a user sees. It should matter most to conformer relaxation, but measuring that means the OpenMM comparison, which needs the server
  • Implicit solvent and short timescales stay the honest limits of the dynamics regardless

Saying out loud when the score did not choose

The two complexes the benchmark gets wrong are a long flexible ligand in a shallow groove, where many placements score within a hair of each other and the search returns whichever won by a rounding error — and a sorted table reads as a verdict. js/poses.js groups the surviving poses into binding modes, compares the top two, and when the gap does not clear a margin says so: the next-best sits N Å away and only M behind, so this ranking is not a preference. The numbers go into the provenance record next to the score, so the caveat travels into any export.

  • Three synthetic knots at known separations cluster into exactly three modes, populations 3/2/1
  • Modes sorted best first, each led by its own best member; spread and RMSD hand-checked
  • A cutoff past every separation gives one mode; under the wobble, one mode per pose
  • A 0.8 gap discriminates, a 0.1 gap does not, and a gap exactly at the margin counts
  • One mode returns null, not true — the absence of a rival is not evidence the score chose
  • Every verdict carries its uncalibrated-margin disclaimer, and the disclaimer is itself asserted
  • Clustering never mutates the caller's array; 88 JavaScript tests and 1438 Python tests passing
  • The margin's value. Calibrating it needs the benchmark, which needs the network — now an explicit queue item rather than a convention left to harden into a fact
  • Nothing about the scoring function changed, and the benchmark was not re-measured: 2 of 4 within 2 Å, median 2.54 Å stands

The torsions the search only sampled coarsely

Iteration 7 tightened a pose as a rigid body. A ligand with rotatable bonds has more freedom than that. js/torsion.js rotates the atoms on one side of a bond about that bond's own axis, pattern-searches every rotatable bond with a shrinking angular step, and alternates rigid-body and torsional passes until a full pass of both stops helping. The geometry checks are exact and make no reference to the scoring function, which is the point of them.

  • Every bond length holds to 1e-4 Å and every bond angle to 1e-4 rad through a rotation
  • The spanning dihedral moves by precisely the angle asked for; the two flanking it move by nothing
  • Hinge atoms and the whole fixed side do not move; a rotation composed with its inverse is the identity
  • A six-carbon sp3 chain yields exactly the three rotatable bonds the geometry implies
  • Never worse than its input, byte-identical determinism, budget respected, rigid ligand costs one call
  • Bug found by the test: the pass loop seeded its best at infinity and so could never stop on pass one
  • 61 JavaScript tests and 1438 Python tests passing
  • Whether this improves the 4-case benchmark — needs structures from the RCSB, and the network is blocked. The published figure stays what was measured: 2 of 4 within 2 Å, median 2.54 Å
  • No internal-strain term: the score sees protein-ligand contacts only, so this polishes a conformer rather than generating one

A docked pose that actually sits in its minimum

The Monte Carlo search ends wherever its last accepted move landed, which is near a minimum rather than in it. js/refine.js adds a pattern search over the six rigid-body degrees of freedom with a shrinking step that accepts only strict improvements, so a refined pose can never score worse than its input. Poses are now refined and re-sorted before they are shown, and the provenance ledger records the gain next to the score.

  • Eight cases on a synthetic carbon cup with a seat known by construction; 47 JavaScript tests in all
  • From four different displacements the score never worsens and the reported gain is never negative
  • A pose knocked 2.3 Å off the seat comes back closer to it than it started
  • Deterministic to the byte, input array never mutated, evaluation budget respected
  • Rotations pivot on the ligand centroid: with translation disabled the centroid holds to 1e-3 Å
  • refineAll re-sorts, because refinement can reorder a ranking
  • Whether this improves the 4-case benchmark — that needs structures from the RCSB, and the network is blocked. The published figure stays what was measured: 2 of 4 within 2 Å, median 2.54 Å
